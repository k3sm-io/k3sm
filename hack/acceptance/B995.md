# Security framework checks on bare Mach-O files: findings

`B995.sh` asks the Security framework directly (`SecStaticCodeCreateWithPath`,
`SecRequirementCreateWithString`, `SecStaticCodeCheckValidityWithErrors` with
`kSecCSStrictValidate | kSecCSCheckAllArchitectures | kSecCSCheckNestedCode`, and
`SecCodeCopySigningInformation`) the questions the root updater's Apple check depends on.
The probe is `hack/acceptance/B995/`. Fixtures are the installed binaries under
`/Library/k3sm` and copies extracted from the published v0.2.3 disk image. Recorded on
2026-10-29 on macOS 27.0.1 (arm64), network on, run as an ordinary user from a login
session.

## Results

The pinned requirement:

```
anchor apple generic and certificate leaf[subject.OU] = "L578HWC325"
and certificate 1[field.1.2.840.113635.100.6.2.6] exists
and certificate leaf[field.1.2.840.113635.100.6.1.13] exists
```

| Check | Installed (5 files) | v0.2.3 disk image copies (5 files) |
|---|---|---|
| pinned requirement | pass | pass |
| pinned requirement `and notarized` (twice) | pass | pass |
| same requirement, another team OU | fail | fail |
| ad-hoc signed copy of `k3sm`, with and without `and notarized` | fail | fail |

The five files are `k3sm`, `k3sm-execshim`, `k3sm-vmhost`,
`libk3sm_getaddrinfo_shim.dylib` and `libk3sm_pathrebase_shim.dylib`.

Wall time per framework call, online: 11 to 100 ms for every file except the `k3sm`
copy read from the mounted image, which took 250 to 350 ms (two runs). The second `notarized` call on a
file was not measurably faster than the first, so these numbers do not show a ticket fetch
that a cache then skips.

The disk image:

- `stapler validate` on the dmg: exit 0, a ticket is stapled.
- `spctl -a -vv -t open --context context:primary-signature` on the dmg: accepted,
  `source=Notarized Developer ID`, team `L578HWC325`.
- `stapler validate` on `k3sm.app` inside the dmg: exit 0.
- `stapler validate` on a bare Mach-O copy: exit 65, no ticket stapled.

Signing information, identical for the installed files and the v0.2.3 copies:

| File | Identifier | Hardened runtime | Entitlements | Info plist |
|---|---|---|---|---|
| `k3sm` | `k3sm-<40 hex>` | yes | none | none |
| `k3sm-execshim` | `k3sm-execshim-<40 hex>` | yes | none | none |
| `k3sm-vmhost` | `k3sm-vmhost-<40 hex>` | yes | `com.apple.security.virtualization` | none |
| `libk3sm_getaddrinfo_shim.dylib` | `libk3sm_getaddrinfo_shim-<40 hex>` | yes | none | none |
| `libk3sm_pathrebase_shim.dylib` | `libk3sm_pathrebase_shim-<40 hex>` | yes | none | none |

## What this means for the updater design

- The framework gives the right verdict for a bare, Developer ID signed and notarized
  Mach-O when online: the pinned team and Developer ID fields pass, a foreign team and an
  ad-hoc signature fail, and `notarized` is satisfied without a stapled ticket.
- Released binaries today carry the identifier codesign derives from the file
  (`<name>-<hash>`) and no `__TEXT,__info_plist` section. A requirement with
  `identifier "io.k3sm.<binary>"` and a version read from the signed info plist both need a
  release pipeline change first: link an info plist into every payload Mach-O and sign with
  an explicit `io.k3sm.<binary>` identifier.
- Hardened runtime is set on every payload file, and only `k3sm-vmhost` carries an
  entitlement, which matches the planned per-binary allowlist.
- A stapled container for the payload exists today: the published dmg carries a ticket,
  and so does the app inside it.

## Owed

These need the network off, a host setting the script never changes, and a root
LaunchDaemon with no GUI session, on macOS 26 and on macOS 27:

- the `notarized` result offline;
- whether a prior online check is cached, and for how long;
- how long a hung ticket lookup takes.
